### 원인과 수정

- 입력을 나눌 때 소수점을 문장 끝으로 읽고 수량을 가구 이름으로 잘못 해석했다. 치수 파서가 축, 단위, 충돌을 함께 검사하고 가구 수량을 따로 읽는다.

- 말에서 축이 생략되면 작은 모델이 침대 치수를 방 치수로 읽었다. 앱이 직전에 실제로 반영한 한 축만 같은 방과 가구의 정정에 사용한다.
- 모델이 편집 요청을 도구 열기로 읽거나 이동할 방 이름을 빼면 문장과 대조한다. 직접 정한 치수와 수량을 모델이 임의로 바꾸지 못하도록 검증한다.
- 응답을 기다리며 방을 이동하거나 배치를 편집하면 기존 답을 버린다. 멈추기를 누르면 요청 적용을 중단한다. 일괄 놓기는 모든 가구의 빈자리를 확인한 뒤 반영한다.

## v5.13.1 UI/UX, 입력, 파일 복구 (2026-11-18)

### 수정과 재현

한글 조합 Enter의 229 코드를 전송과 구별하고 숫자 증감과 전역 단축키에도 같은 방어를 적용했다. 1,500자 한도를 표시하고 빈 숫자는 이전 값으로 복원한다. 숫자 오류와 입력을 ARIA로 연결했다. 메뉴는 방향키, Home/End, Tab, Esc, 새 대화 확인은 취소, Esc, 바깥 클릭, 초점 복귀를 지원한다. 알림은 키보드 초점 중 사라지지 않고 닫기 단추를 제공한다. 초점이 남은 채 포인터가 떠나거나 알림 내용이 바뀌는 경우도 포함한다. 다운로드 동의창은 방과 대화를 inert로 둔다. 동작 줄이기 설정은 대화 스크롤에도 적용한다.

## v5.7 말귀, 겹치지 않는 집, 화장실 설비, 방 돌리기 (2026-11-16)

요청: 사용자가 Gemma 4 E2B로 실제로 쓰다 막힌 대화 화면 네 장과, 말로 덧붙인 두 가지다.

1. “화장실 옆에 방하나 추가하자. 거기는 거실임” → 화장실이 하나 더 생겼다. 답은 “거실 공간을 추가했어요”였다.
2. “왜 화장실로 생성하는거야”, “아니 거실이라니까 왜 자꾸 화장실로 고정하냐고!!!!” → 두 번 다 “방 유형과 가로, 세로를 알려주세요”만 되풀이했다.
3. “거실이라고 그리고 거기에 소파랑 밥먹을 수 있는 식탁이 있었으면 좋겠어. 거실 평수는 대략 6평정도야” → 식탁 초안만 만들었다.
4. 도구에서 직접 거실로 바꾸자 방이 옆 화장실 위로 겹쳤고, “거실로 바꿨는데 겹치잖아...”에는 “겹치거나 벽을 넘은 가구가 없어요”라고 답했다. 이름은 계속 “나의 화장실”이었다.
5. “한 6평정도 됨” → “거실을 가로 4.92m, 세로 4.03m, 천장 2.5m로 반영했어요”와 주황색 “면적만으로 가로, 세로는 알 수 없어…”가 떴다.
6. “왜 화장실은 수정이 안 되냐”, “집 수정 모드에서 방 하나를 골라 방 자체를 돌리는 기능도 있었으면 좋겠다.”

### 원인

모델이 아니라 앱의 검증이 틀린 경우가 많았다. 1번과 2번에서 Gemma 4 E2B는 거실을 골랐다.

| 본 것 | 원인 |
|---|---|
| 화장실이 하나 더 생김 | `detectRoomType`이 문장에 나온 공간 이름 가운데 표의 앞쪽 것(화장실)을 골랐다. “화장실 옆에”가 자리를 가리키는 말인지 보지 않았고, 이 값으로 모델이 고른 거실을 뒤집었다 |
| 한 일과 다른 답 | 앱이 유형을 바꿔 놓고도 모델이 쓴 답을 그대로 보여 줬다. “방 초기화할래”에서도 비우기를 막아 놓고 “모든 가구를 비웠습니다”를 보여 줬다 |
| 따져도 같은 안내 | “왜 화장실로”의 화장실을 다시 유형으로 읽어, 지금 방이 이미 화장실이니 바뀐 것이 없다고 보고 기본 안내를 냈다. 모델이 고른 거실은 “문장에 적힌 화장실 유지”로 막았다 |
| 식탁만 처리 | 한 턴에 방 계획 하나 또는 가구 초안 하나만 만들 수 있었다. 가구 이름이 있으면 가구 이야기로만 읽어 방 유형과 면적을 버렸고, 초안은 하나뿐이라 소파가 빠졌다 |
| 방이 겹침 | 방 크기를 바꿔도 집 도면의 자리(중심)는 그대로였다. 1.8m 방이 5.5m가 되면 양쪽으로 늘어나 옆방을 덮었다. 규칙은 “경고한다”였다 |
| “겹치잖아”에 가구만 확인 | 자리 정리가 가구의 겹침만 봤다 |
| 이름이 안 바뀜 | 유형 이름을 딴 기본 이름을 만들 때 한 번만 붙였다 |
| “6평”을 못 알아들은 듯한 답 | 면적은 맞게 읽었다(19.8m²). 하지만 답에 6평이 없고, 4.92m 같은 값과 경고 색의 “알 수 없어”만 보였다 |
| 화장실이 수정 안 됨 | 변기, 세면대, 샤워 자리는 가구가 아니라 그림이어서 고를 수 없었다. 집 전체에서는 화장실 바닥을 색과 상관없이 타일로만 칠했다. 큰 방과 겹친 화장실은 눌러 고르기도 어려웠다 |

### 바꾼 것

- **공간 이름의 역할을 가려 읽는다**(`room-consult.js`의 `roomMentions`). 뒤에 “옆, 앞, 오른쪽, 에 붙여”가 오면 자리(ref), “말고, 아니라, 대신”이 오거나 “왜 … 로 만들어/고정/생성”이면 아니라고 한 이름(neg), 나머지는 만들거나 바꿀 유형(new)이다. “거실이라니까”, “거실임”, “거실로 바꿔”는 못 박은 말로 본다. `detectRoomType`은 new만 고른다. 모델이 고른 유형은 문장의 new 가운데 있으면 따르고, ref, neg로만 나온 이름은 모델이 골라도 쓰지 않는다(`interpret.js`의 `pickRoomType`).
- **기준 공간 옆에 붙인다.** “화장실 옆에”, “침실 오른쪽에”는 그 유형의 공간(이름을 말했으면 그 공간)을 기준으로 삼는다(`planner.refSpace`, `ops.addSpace`의 `anchor`). 새 공간은 정한 크기로 자리를 잡는다. 말한 벽이 막혀 있으면 다른 벽에 붙이고 답에서 알린다. 그런 공간이 없으면 지금 방에 붙이고 없었다고 알린다. 답은 “나의 화장실 오른쪽에 나의 거실을 붙였어요. 가로 5.5m, 세로 4.5m예요”처럼 실제로 붙은 자리를 넣어 앱이 쓴다.
- **따지는 말을 명령으로 읽지 않는다.** 아니라고만 한 문장은 앞의 사용자 말에서 바라던 유형을 찾아 바꾸고 “제가 잘못 읽었어요”라고 답한다(`planner.repairPlan`). 찾지 못하면 바꾸지 않고 묻는다. 지금 방이 이미 그 유형이 아니면 지금 무엇인지 알린다. 가리키는 것이 없는 불만(“아니 그게 아니라”)은 떠 있는 초안 이야기로 받지 않고 되묻는다. 유형 없이 “방 하나 더 만들어줘”라고 하면 만들지 않고 유형을 묻는다.
- **한 문장의 여러 요청을 나눈다**(`planner.splitRequest`, `mergePlans`). 마디마다 방 이야기인지 가구 이야기인지 가르고, “랑, 하고, 와”로 이은 가구는 따로 초안을 잡는다. 방 마디의 숫자는 방에, 가구 마디의 숫자는 그 가구에만 쓴다. “침대 옆에 협탁”, “책상에 놓을 스탠드”의 앞 이름은 자리로 읽어 여러 가구로 나누지 않는다. 첫 초안을 띄우고 나머지는 `app.queue`에서 기다린다. 앞의 것을 놓으면 다음이 뜨고, **모두 놓기**(“둘 다 놓아줘”)는 한꺼번에 놓는다. 되돌리기 한 번으로 물린다.
- **한 일과 다른 답을 내지 않는다.** 모델이 쓴 답은 앱이 바로잡은 것이 없고, 바뀐 것 없이 “했어요”라고 끝나지 않을 때만 쓴다. 색만 바꾼 턴은 치수 대신 “소파 색을 네이비로 바꿨어요”라고 답한다.
- **면적을 받아 준다.** “6평(약 19.8m²)에 맞춰 거실을 가로 4.9m, 세로 4.05m로 잡았어요. 한쪽 벽 길이를 알려주면 그 길이에 맞춰 다시 나눌게요.” 치수는 5cm 단위로 다듬고, 다듬은 넓이가 말한 면적에서 2% 넘게 벗어나면 다듬지 않는다. 경고 색 문구를 없애고 **가로 5m로**, **정사각형에 가깝게** 칩을 붙였다. “6평, 가로 5m”처럼 한쪽을 함께 말하면 나머지를 면적으로 구한다.
- **크기를 바꿔도 겹치지 않는다**(`ops.reseatSpace`). 이웃이 맞닿아 있던 벽은 그 자리에 두고 반대쪽으로 늘이거나 줄인다. 양쪽에 이웃이 있으면 먼 쪽 이웃과 거기에 이어진 공간을 달라진 길이만큼 함께 옮긴다. 그래도 겹치면 가장 적게 움직이는 방향으로 민다. 이미 겹친 공간은 “겹치잖아”라고 하거나 배치 확인과 집 전체 도구의 단추로 떼어 놓는다(`ops.separateSpaces`). 배치 확인은 겹친 공간도 함께 보여 준다.
- **기본 이름이 유형을 따라간다.** “나의 화장실”을 거실로 바꾸면 “나의 거실”이 된다. 같은 이름이 있으면 번호를 붙인다. 직접 지은 이름은 그대로 둔다.
- **화장실 설비는 가구다.** 변기, 세면대, 샤워부스를 가구 종류에 더했다(23종 72가지). 화장실을 만들거나 유형을 화장실로 바꾸면 예전 그림과 같은 자리에 가구로 놓이고, 그 뒤에는 고르고 끌고 돌리고 빼고 **가구 고르기 › 욕실**에서 다시 놓는다. 화장실이 아니게 되면 손대지 않은 설비만 치운다. 화장실 바닥은 기본이 타일이고 다른 공간처럼 바꾼다. 사진 판별은 그대로 20가지다.
- **방을 통째로 돌린다**(`ops.rotateSpace`). 집 전체에서 고른 공간의 이름표와 집 전체 도구의 공간 줄에 돌리기 단추를 두었고, “이 방 돌려줘”, “화장실 돌려줘”도 된다. 가로와 세로가 바뀌고 가구와 아바타가 함께 돈다. 옆 공간과 맞닿은 벽을 지키며 자리를 다시 잡는다. 그 공간에 직접 정해 둔 문은 벽이 달라지므로 자동 문으로 돌아간다. 네 번 돌리면 처음과 같다.
- **예전 저장본을 손본다**(저장 형식 v5, `ops.migrateLegacy`). v4 이하를 불러올 때 한 번, 화장실 설비를 가구로 옮기고 타일 바닥을 바닥 색으로 옮기며, 유형과 어긋난 기본 이름을 맞추고, 겹친 채 저장된 공간을 떼어 놓는다. 사용자의 저장 상태(거실인데 이름은 “나의 화장실”이고 화장실과 겹친 집)를 그대로 넣어 확인했다.

### 만들면서 찾아 고친 문제

- 작업 중에 `origin/main`에 다른 세션의 커밋 8개가 올라왔다(목록에 없는 물건, 다른 가구의 삭제와 회전, 조사, 색 이름, 기본 모델 변경). 같은 파일이라 일곱 군데가 충돌했고 양쪽 동작을 모두 남겨 합쳤다. 합친 뒤 그쪽 테스트 21개도 통과한다.
- 합치고 보니 목록에 없는 물건 찾기가 이번 문장들을 가로챘다. “방하나 추가하자”의 “방하나”, “왜 자꾸 이상하게 만들어”의 “자꾸”, 가구를 고른 채 “방향 돌려줘”의 “방향”, “앉을 만한 거 하나 놓고 싶어”의 “거”를 물건 이름으로 읽어 “거는 아직 가구 목록에 없어요”라고 답했다. 마지막 것은 기존 평가 문장이기도 하다. 물건을 대신하는 말과 붙여 쓴 수량, 속성, 부사를 물건 이름에서 뺐고, 방을 추가하자는 말은 이 검사보다 먼저 읽는다.
- 실제 Gemma 4 E2B에서 두 가지를 더 찾았다. “거실 말고 침실로 바꿔줘”에 모델이 공간 이동을 골랐는데 “바꿔”가 이동의 근거로 통해 화장실로 옮겨 갔다. 이제 그 공간의 이름이나 유형이 문장에 있을 때만 옮긴다. 초안을 띄워 둔 채 “방 하나 더 만들어줘”라고 하면 초안 도구를 다시 띄웠다. 이제 유형을 묻는다.
- 실제 Gemma 3 1B는 초안을 띄워 둔 채 “아니 그게 아니라”에 놓기를 골랐고, 막힌 뒤에는 초안 치수를 다시 읊었다. 가리키는 것 없는 불만은 모델 경로에서도 되묻게 했다.
- 프롬프트에 예시 두 개를 더했더니 E2B 응답 시간의 중앙값이 6.6초에서 7.9초로 늘었다. 앱의 검증만으로 같은 결과가 나와서 예시는 빼고 한 줄 안내만 남겼다. 지금은 6.9초다.
- 여러 초안 안내를 “방에 띄웠어요”라고 썼는데 집 전체 보기에서는 초안이 도면에 보이지 않는다. “규격을 골라 보세요”로 바꿨다.
- 2D 변기 기호에 물탱크와 변기를 잇는 선이 그어졌다(경로를 이어 그림). 접힌 배치 확인의 요약은 겹친 공간을 세지 않았다. 둘 다 고쳤다.

### 설계 규칙 대조 (`open-design`, `unslop`, `humanize-korean`)

- 상태: 배치 확인은 문제 없음, 겹친 공간, 겹친 가구, 둘 다를 각각 보여 준다. 방 돌리기와 공간 붙이기는 실패하면 알림으로 이유를 말하고 기록을 남기지 않는다. 공간 12개에서 이름표가 아이콘으로 접혀도 고른 공간의 이름표는 접지 않아 돌리기 단추가 남는다. 320px에서도 이름표가 한 줄에 들어간다.
- 접근성: 돌리기 단추에 이름(“선택한 방 90도 돌리기”, “나의 거실 90도 돌리기”)과 풀이말을 달았다. 기존 방 편집 단추와 같은 높이와 포커스 표시를 쓴다. 겹침 경고는 색만이 아니라 글과 단추로 알린다.
- 디자인 방향: 새 색과 새 아이콘 계열을 들이지 않았다. 돌리기는 가구 도구 막대와 같은 Lucide `rotate-cw`, 욕실 설비는 `toilet`, `droplets`, `shower-head`다. 줄자 노랑은 그대로 직접 정한 치수와 선택 표시에만 쓴다.
- 문구: 한글 빠른 규칙으로 새 문장을 대조했다. 연결어미 뒤 쉼표 한 곳(“띄웠고, 놓으면”)을 두 문장으로 나눴고, “알 수 없어”처럼 실패로 읽히는 말을 다음에 할 일로 바꿨다. 조사는 `josa()`로 붙인다.

### 확인 범위와 한계

- 실제 모델은 Mac의 Chrome(WebGPU Metal)에서 f16과 f32 빌드를 돌렸다. 실제 휴대 기기와 다른 GPU에서는 돌리지 못했다.
- 사진 판별(SigLIP)은 바꾸지 않았다. 욕실 설비는 사진 판별 대상이 아니어서 변기 사진을 올리면 20가지 가운데 가까운 후보가 나온다.
- 문장 나누기와 역할 읽기는 정해 둔 말(“옆, 말고, 아니라, 라니까, 랑, 하고”)에 기대는 규칙이다. 이름 없이 말한 둘째 가구(“앉을 것 하나랑 책 꽂을 데”)는 모델이 고른 하나만 초안이 된다. 표에 없는 자리 말(“화장실 쪽으로 하나 더”)은 지금 방에 붙이거나 유형을 묻는다.
- 사방이 막힌 방을 키우면 밀어낼 자리를 찾지 못할 수 있다. 그때는 겹친 채 두고 경고와 떼어 놓기 단추를 보여 준다.
- 방 돌리기는 90° 단위이고 방은 직사각형이다.

## 사진+설명 연결, 상담과 사진 Worker 분리 (2026-11-16)

최신 원격 main `78a629e`의 목록 밖 물건, 색, 가구 대상 처리 수정을 기준으로 작업했다. 원래 체크아웃의 다른 개발자 미완성 변경과 미푸시 커밋은 건드리지 않았다.

- 사진만 보낼 때뿐 아니라 사진과 글을 함께 보내도 먼저 SigLIP을 실행한다. 판별한 가구 초안에 설명을 기존 모델/규칙 경로로 반영하며, 설명을 사용자 턴에 두 번 넣지 않는다. 확신이 낮으면 설명을 보관하고 후보 선택 후 반영한다. 후보 종류를 바로잡을 때도 이미 직접 정한 치수와 색을 보존한다.
- `ai.js`가 상담과 사진을 별도 Worker에 보낸다. 한쪽 큐, 취소, 오류가 다른 쪽의 준비와 추론을 멈추지 않는다. 종료한 Worker의 늦은 이벤트는 무시한다. Worker 실패를 사용자 취소로 오인해 준비 안내가 남는 경로도 고쳤다.
- 진행률과 오류를 종류별로 보관한다. 아일랜드는 사용자가 시작한 사진 작업을 먼저 알리고 완료와 취소 후 진행 중인 Gemma 안내로 돌아간다. 같은 사진을 다시 고르거나 판별 중 방을 옮겨도 새 사진과 다른 방의 초안을 덮어쓰지 않는다. 사진+글도 휴대 기기 다운로드 전 동의를 지킨다.
- UI는 기존 종이, 먹색, 줄자 방향을 유지했다. 준비 중, 실패, 재시도, 후보 선택 상태와 입력창 접근을 `open-design` 상태와 접근성 규칙으로 대조하고 한글 빠른 규칙으로 문구를 다듬었다. 단순 연결 수정이라 별도 기획 페이지는 추가하지 않았다.

## 조사와 바뀐 것이 없을 때의 답

## 고른 가구와 다른 가구를 말할 때의 삭제와 회전

문제: 책상을 고른 채 “침대 빼줘”라고 하면 책상이 지워졌다. “의자 90도 돌려줘”는 책상을 돌렸다. 삭제와 회전이 문장에 적은 가구 이름을 보지 않고 늘 고른 가구에 적용됐다(`planner.js`의 `planMeta`, `interpret.js`의 `actionPlan`, `store.js`의 `runAction`). 아무것도 고르지 않고 “소파 빼줘”라고 하면 방에 소파가 없는데도 새 소파 초안을 만들었다.

바꾼 것: `actionSubject`가 문장에 적은 가구를 찾는다. 이름이 없거나 고른 가구와 같으면 지금처럼 고른 가구에 한다. 다르면 방에서 그 종류를 찾아 하나면 그 가구에 하고, 여럿이면 실행하지 않고 도면에서 고르라고 하며, 없으면 “이 방에는 소파가 없어요”라고 답한다. 같은 종류의 초안이 떠 있으면 지금처럼 초안 이야기로 넘긴다. 계획은 대상 가구의 `arg.id`를 넘기고, store는 그 가구에 적용한다. 고르지 않은 가구를 뺐으면 고른 가구는 그대로 둔다. 규칙 경로와 모델 경로가 같은 함수를 쓴다.

확인: 단위 테스트 2개를 더해 109개가 통과했다. 브라우저 테스트는 커밋 전에 한 번 돌렸다.

## 목록에 없는 물건을 말할 때

요청: Gemma 3 1B로 “이미 있는 책상에 컴퓨터를 추가해 달라”고 하자 새 책상 초안이 생겼다. 우리 가구 목록에 있는 것은 그대로 처리하고, 없는 것은 무엇이든 따로 처리할 것.

### 원인

가구 목록에 컴퓨터가 없고, 문장에서 아는 이름은 “책상”뿐이었다. 앱은 문장에 적힌 가구 이름을 따르므로 책상으로 정했고, “추가”를 새 가구를 뜻하는 말로 읽어 새 책상 초안을 만들었다. 모델 스키마의 `furniture`는 20종과 `none`만 고를 수 있어 모델이 컴퓨터라고 답할 길도 없었다. 목록에 없는 말은 경우에 따라 무시되거나(“어떤 가구인지 알려주세요”), 고른 가구에 대한 말로 읽혀 그 가구를 바꾸거나 지웠다.

### 바꾼 것

`src/app/planner.js`의 `objectsOf`가 “놓아줘, 추가, 빼줘, 있어?” 같은 동사 바로 앞의 낱말을 목적어로 읽는다. 목적어가 목록의 가구면 지금처럼 처리하고, 아니면 이름과 상관없이 목록에 없는 물건으로 본다. 그때는 초안을 만들지 않고 고른 가구도 바꾸지 않으며, 없다고 답하고 가구 고르기를 권한다. “책상에”와 “책상 위에”처럼 놓을 곳을 말했으면 그 가구 위에 올릴 수 없다고 답한다. “컴퓨터랑 책상”처럼 목록의 가구와 함께 말하면 책상은 처리하고 컴퓨터는 뺐다고 덧붙인다.

`src/estimator.js`의 표(27가지)는 목록에 없다고 미리 아는 이름이다. 모든 경우를 적은 목록이 아니고, 목록의 이름을 품은 말(“안마의자”, “스탠드 에어컨”)을 의자와 조명으로 읽지 않게 하고 다른 가구 위에 두는 물건인지 알려 줄 때만 쓴다. “컴퓨터 책상”, “컴퓨터책상”처럼 뒤에 목록의 이름이 오면 꾸밈말로 보고 책상으로 처리한다. 지시어(“이거”), 방과 공간 이름, 수량과 자리 말은 목적어로 보지 않는다.

모델 경로(`src/app/interpret.js`)도 같은 검사를 지난다. 모델이 책상이나 삭제를 골랐어도 목록에 없는 물건이면 실행하지 않고, 바로잡은 내용에 “목록에 없는 물건(컴퓨터)이라 가구를 만들지 않음”을 남긴다.

### 확인

단위 테스트를 더했다(`planner.test.js` 2개, `interpret.test.js` 1개). 고른 책상에 “책상에 컴퓨터 추가해줘”, “모니터 빼줘”, 사전에 없는 “트램펄린 하나 놓아줘”, “커피머신, 토스터 추가해줘”, 꾸밈말인 “컴퓨터 책상 하나 놓아줘”, 방 이야기인 “컴퓨터 하는 서재 하나 추가해줘”와 “피아노 치는 방으로 꾸며줘”를 확인했다.

실제 화면에서 써 보다가 “컴퓨터를 책상위에 만들어줘”가 새 책상 초안을 만드는 것을 찾았다. “만들어, 올려, 설치, 깔아” 같은 동사를 빠뜨렸고, 놓을 곳을 목적어 앞에서만 찾았기 때문이다. 동사를 더하고 놓을 곳은 목적어 앞뒤에서 모두 찾게 했으며, “책상 위에”처럼 띄어 쓴 놓을 곳은 목적어로 읽지 않게 했다. “모니터를 책상 위에 올려줘”도 같은 답을 받는다.

동사 없이 이름만 말한 문장(“트램펄린”, “큰 트램펄린”)도 잡는다. 원래 처리로 방, 가구, 초안 중 바뀌는 것이 없을 때만 목록에 없는 물건으로 본다. 그래서 “퀸”(침대 규격), “초록색”(가구 색), “서재”(공간 유형)는 지금처럼 처리된다. 인사와 대답, 색과 분위기 말(“모던”), 크기 말(“넓게”), 서술어로 끝나는 말(“도와줘”, “더 크고 넉넉하게”의 “크고”)은 물건 이름으로 보지 않는다. 사전에 있는 이름(“안마의자”)은 바뀌는 것이 있어도 목록에 없다고 답한다. 기존 모델 경로 테스트가 “크고”를 물건으로 읽는 실수를 잡아 이 규칙을 더했다.

**한계:** 모델 프롬프트와 스키마는 바꾸지 않았다. 앱의 검사만 바꿨으므로 실제 Gemma로 다시 재지 않았다. 목적어가 동사 뒤에 오는 문장(“놓아줘, 트램펄린”), 동사 목록에 없는 말(“갖고 싶어”), 이름 앞에 꾸밈말이 둘 이상 붙은 문장은 잡지 못한다. 모델이 목록 밖 물건과 그 이름을 직접 알리게 하는 스키마 변경은 실제 모델 평가(`eval/chat/run.mjs`)와 함께 다음에 한다.

## v5.6 대화 열 절반, 화면 가운데 아일랜드, 방 밖 아바타, 휴대 기기에서 받기 전에 묻기

요청(v5.5를 써 본 뒤): 모델 준비 표시(아일랜드)는 원하던 모양이니 화면 가운데에 정렬할 것. 사람 모형은 기본으로 방 바깥쪽에 서 있게 하고 지금처럼 끌어서 옮기게 할 것. 컴퓨터에서는 채팅 영역이 화면 중간까지 차지하게 하고 경계를 잡고 끌어 너비를 바꾸게 할 것. 모델이 약 600MB라 모바일에서는 부담되니, 처음 쓰는 사람에게 내려받기가 필요하다는 팝업을 띄우고 단추를 누르면 그때부터 받게 할 것.

### 요청을 옮기면서 정한 것

- **누구에게 묻는가:** 휴대 기기(휴대폰과 태블릿의 브라우저 소개 문자열, 터치가 되는 Mac 소개 문자열, 이동통신 연결)에서 모델이 다 보관돼 있지 않을 때만 묻는다. 컴퓨터는 요청대로 묻지 않고 준비한다.
- **문구:** 제목은 요청대로 “상담 모델을 먼저 받아야 해요”다. 받지 않아도 정해진 표현은 규칙으로 알아듣는다는 사실을 같은 팝업에 적었다. 모델이 없으면 못 쓰는 것처럼 말하지 않으려는 것이다.
- **사진 판별 모델:** 요청에는 없지만 같은 이유로, 휴대 기기에서는 사진을 보내도 약 150MB인 사진 모델을 저절로 받지 않는다. 크기를 적어 둔 `사진으로 종류 확인` 단추를 눌러야 받는다. `나중에`를 고른 뒤에도 마찬가지다.
- **아일랜드의 세로 자리:** 화면 가운데는 대화 머리의 단추와 방 위 길잡이가 만나는 곳이다. 같은 줄에 두면 단추를 가리므로 그 줄 바로 아래(위에서 76px, 모바일 62px)에 둔다.
- **아바타가 서는 자리:** 방 바깥 앞쪽 왼 모서리 옆이다. 기본 3D 시점(오른쪽 앞 위)에서 몸이 방 안의 무엇도 가리지 않고 벽 뒤에 숨지도 않는 자리는 화면 왼쪽 끝과 오른쪽 끝뿐이고, 그중 카메라에 가까워 크게 보이며 벽 끝과 나란히 서는 쪽을 골랐다.
- **받기 전에 묻는 방식의 근거:** Chrome의 내장 AI 안내서(“It's best practice to alert the user to the time required to perform these downloads.”, 단추를 누른 뒤 받기 시작하고 진행률을 보여 줌)를 읽고 정했다. 주소는 `docs/design-direction.md`에 있다. Apple의 권한 요청 안내는 본문을 읽지 못해 근거로 쓰지 않았다.

### 만들면서 찾아 고친 문제

- **다시 와도 또 물음:** 실제 모델로 받은 뒤 다시 열자 팝업이 또 떴다. 조각 목록 파일 이름을 `ndarray-cache.json`으로만 찾았는데 Gemma 3 1B는 `tensor-cache.json`이었다. 둘 다 찾게 고치고 실제 캐시에서 다시 확인했다.
- **집에서는 벽 뒤에 숨는 아바타:** 앞쪽에 화장실이 붙은 집에서 아바타가 화장실의 높은 왼쪽 벽 뒤에 서서 집 전체 3D에 보이지 않았다. 카메라 쪽 3m 안에 다른 공간이 있는 자리는 건너뛰게 했다.
- **아주 작은 방:** 사방이 막힌 1×1m 방에서 방 안에 세울 자리를 계산하다 벽 밖으로 나갔다. 단위 검사가 잡았다.
- **320px에서 잘린 `모델 받기`:** 대화 머리의 상태 줄이 길어 단추가 화면 밖으로 밀렸다. 설명을 말줄임하고 단추는 끝까지 남긴다.
- **대화를 가득 펼친 모바일:** 아일랜드가 대화 머리(이름과 상태 줄)를 덮었다. v5.5부터 있던 문제다. 가득 펼치면 머리 아래로 내린다.
- **먹색끼리 붙어 보임:** 아일랜드가 사용자의 먹색 말풍선 위에 뜨면 한 덩어리로 보였다. 종이색 테를 둘렀다.
- **반 폭에서 줄이 바뀌는 알림:** 알림이 화면 가운데에서 시작해 남은 절반 폭에서 줄을 바꿨다(v5.5부터). 글 길이만큼 폭을 잡게 했다.
- **몸에서 떨어진 이름표:** 집 전체 2D의 키 이름표가 몸에서 0.85m 위에 떠 있었다. 몸이 차지한 범위에 붙이고, 방 앞쪽 바깥에 서 있으면 몸 아래에 둔다.
- **Enter 한 번에 600MB:** 팝업을 열 때 초점을 `모델 받기`에 두면 Enter 한 번에 받기 시작한다. 초점은 팝업 자체에 두고 Tab으로 단추에 간다.

### 설계 규칙 대조 (`open-design`, `unslop`, `humanize-korean`)

- **상태:** 팝업은 처음 받기와 이어서 받기 두 가지 글을 가진다. 캐시를 읽을 수 없으면 전체 크기로 묻고, 저장소가 막혀 `나중에`를 기억하지 못하면 다음 방문에 다시 묻는다. 받기를 누른 뒤의 실패는 아일랜드가 이유와 `다시 시도`로 알린다.
- **접근성:** 팝업은 `dialog`, `aria-modal`이고 제목과 설명이 이름으로 연결된다. 초점은 두 단추 사이에서만 돌고 Esc와 바깥 누르기는 `나중에`다. 단추 높이는 44px이다. 흐린 글(먹색 위 종이색 64~72%)의 대비는 7:1을 넘는다. 대화 폭 손잡이는 `separator` 역할과 값을 그대로 가진다.
- **움직임:** 팝업과 아일랜드는 같은 나타나기 움직임 하나만 쓴다. 움직임 줄이기 설정에서는 바로 나타난다.
- **문구:** “대화 머리의 ‘모델 받기’”는 화면에 없는 말이라 “대화 위쪽 ‘모델 받기’”로 바꿨다. 팝업과 알림의 한글은 낱말 중간에서 줄이 바뀌지 않게 했다.

### 실제 모델 (Mac Chrome 헤드리스, WebGPU Metal)

- **휴대 기기 크기에서 묻고 받기:** 390×844, Android Chrome 소개 문자열, 새 프로필로 프로덕션 빌드를 열었다. 팝업이 뜬 뒤 3초 동안 모델 저장소 요청은 0건이었다. `모델 받기`를 누르자 팝업 자리에서 “상담 모델 받는 중 0%”로 이어졌고 33초 뒤 준비가 끝났다. “두 명이 앉는 낮은 소파”, “벽은 좀 더 따뜻한 느낌이면 좋겠어”를 Gemma 3 1B가 해석했다.
- **다시 방문:** 묻지 않았고 모델 저장소 요청 0건, 2초 만에 준비됐다.
- **받다 만 모델:** 캐시에서 조각 두 개를 지우고 열자 “남은 크기 약 58MB, 이어서 받기”로 물었고, 누른 뒤 그 두 조각만 받았다.
- **컴퓨터 18문장:** `eval/chat/run.mjs`로 같은 18문장을 보냈다. 변경 내역이 v5.5와 문장마다 같았다(모델이 해석 18/18, 기대와 다른 결과 2개도 같은 문장). 문장당 2.3초, 처음 준비 30초, 오류 0건. 묻지 않고 받기 시작했고 아일랜드가 펼쳐진 채 나타났다. 결과는 `eval/chat/results/gemma3-1b-v56.json`.
- **사진 판별(SigLIP):** 컴퓨터에서는 침대 사진을 보내자 바로 판별해 침대 93%로 초안을 띄웠다. 휴대 기기 크기에서는 저절로 받지 않았고, `사진으로 종류 확인`을 누른 뒤 의자 46%, 식탁 35%, 커피 테이블 14%로 후보를 보여 줬다.
- 다른 상담 모델(Qwen3 0.6B f32, Gemma 4 E2B)은 다시 돌리지 않았다. 바꾼 것은 받기 전 확인과 캐시 대조이고 해석 경로는 그대로다.

### 화면

1440×900, 1024×720, 900×700, 390×844, 320×640에서 첫 화면, 아일랜드(접힘, 펼침, 실패, 완료), 알림, 팝업, 대화, 방 밖 아바타(3D와 2D), 집 전체, 공간 고르기, 접은 대화를 찍어 한 장씩 보고 위의 문제를 고쳤다. `docs/screenshots/`의 22장을 새 화면으로 바꾸고 `model-ask`를 더했다(23장). `model-fixes`, `photo`, `mobile-photo`는 실제 모델과 CC0 사진으로 찍었다.

### 확인 범위와 한계

- 휴대 기기는 실제 기기가 아니라 헤드리스 Chrome에 휴대폰 소개 문자열과 화면 크기를 넣어 확인했다. 실제 아이폰과 안드로이드에서 팝업 뒤에 모델이 도는지는 v5.5와 같이 확인하지 못했다.
- 휴대 기기 판별은 브라우저 소개 문자열과 터치 점 개수에 기댄다. 데스크톱 모드로 연 휴대폰은 컴퓨터로 보여 묻지 않고 받는다. 이동통신 연결 여부는 Chrome 계열에서만 알 수 있고, 휴대폰에 테더링한 컴퓨터는 구별하지 못한다.
- 아일랜드와 알림은 화면 가운데에 뜨므로 대화 열 맨 위의 글을 잠깐 가린다. 컴퓨터에서 처음 받을 때 펼쳐진 안내는 창이 낮으면(1024×720) 인사 말풍선의 오른쪽을 7초 동안 덮는다.
- 아바타를 방 안팎으로 옮겨 놓으면 도면과 3D의 축척이 놓는 순간 다시 맞춰져 화면이 한 번 움직인다. 3D에서 시점을 직접 돌린 뒤에는 다시 맞추지 않는다.
- 아바타가 서는 자리는 기본 3D 시점을 기준으로 골랐다. 시점을 돌리면 벽 뒤로 갈 수 있다.

## v5.5 상담 대화 열, 모델 아일랜드, 벽의 +로 공간 붙이기, 문 편집

### 만들면서 찾아 고친 문제

- **문 앞을 1cm 걸친 설비:** 문이 두 벽에 난 1.8×2.2m 화장실에서 여유 영역 넓이만 견주다 보니 변기가 문 앞 통로를 1cm 침범하는 안이 뽑혔다. 단위 검사가 잡았다. 통로를 막는 넓이에 1000배 가중치를 줬다.
- **폭을 바꾸면 문이 밀림:** 벽 끝에서 23cm에 둔 문의 폭을 80→70cm로 줄이면 가운데가 고정돼 거리가 28cm로 바뀌었다. 직접 옮긴 문은 폭을 바꿔도 벽 끝에서의 거리(경첩 쪽)를 지키게 했다.
- **320px에서 문을 못 누름:** 문 막대에 밀려 내려온 방 이름표가 문을 덮었다. 막대 밑에 깔리는 이름표는 밀지 않고 잠시 숨긴다. `+` 손잡이도 문 위에 놓이지 않고 벽을 따라 비킨다(같은 검사가 다시 잡았다).
- **받침 없는 색 이름:** “네이비로 바꿔줘”가 규칙 경로에서 색을 바꾸지 않았다. `으로 바꿔`만 찾고 `로 바꿔`를 놓치던 것이다. 모델 경로의 같은 규칙도 고쳤고, 색만 바꾼 답은 “나의 소파 색을 네이비로 바꿨어요.”라고 말한다.
- **작은 모델의 잘못된 분류:** Qwen3 0.6B가 소파 초안을 가리키는 중의 “네이비로 바꿔줘”, “앉는 부분이 깊었으면 좋겠어”를 방 이야기로 분류해 아무것도 바꾸지 않았다. 가구를 가리키는 중에 방에서 바뀐 것이 없고 문장에 방을 가리키는 말도 없으면 지금 대상인 가구 이야기로 다시 읽는다(`interpret.js`, 바로잡은 내용에 남긴다).
- **Safari에서 Esc가 안 먹음:** Safari는 버튼을 눌러도 초점을 주지 않아, 펼친 아일랜드가 Esc로 접히지 않았다. WebKit 검사가 잡았다. 포인터가 올라와 있거나 초점이 어디에도 없을 때도 접는다.
- **창이 뜨자마자 누른 Esc:** 공간 고르기 창이 그려진 뒤에야 Esc를 듣기 시작해 빠른 입력을 놓쳤다. 그리기 전에 붙인다.
- **이미지 저장 실패:** 이름표 상자를 넓히는 코드가 상수를 다시 대입해 집 전체 이미지 저장이 멈췄다. 기존 검사가 잡았다.
- **좁은 데스크톱:** 대화 열을 넓히자 1024px에서 위 도구 줄이 넘쳐 방 이름이 사라졌다. 방 쪽 폭에 따라 크기 표시 → `공간 추가` 글자 → 다른 범위의 이름 순서로 접고, 대화 폭은 방 쪽에 520px을 남기는 범위로 묶었다. 대화를 아래 시트로 내리는 기준을 760px에서 900px로 올렸다.
- **CI에서만 두 줄이 된 입력창:** 첫 배포 실행이 320px 검사에서 실패했다. CI의 글꼴이 더 넓어 입력창 안내 문구가 두 줄로 넘치고 입력창이 64px로 커졌다(로컬에서는 한 줄). 본문 글꼴을 막고 넓은 글꼴을 넣은 조건으로 로컬에서 재현했다. 안내 문구는 글꼴과 무관하게 한 줄을 지키고 넘치면 말줄임하게 했다.
- **메모와 답이 두 번 나옴:** 답 아래 주황색 메모(`turn.note`)가 두 번 그려지던 기존 실수를 고쳤다. 답을 쓰는 중에는 “규칙으로 처리” 표시가 먼저 뜨지 않게 했다.

### 설계 규칙 대조 (`open-design`, `unslop`, `humanize-korean`)

- 아일랜드의 알림 자리(`role=status`)를 늘 깔아 두고 단계가 바뀔 때만 글을 바꾼다. 끝을 알 수 없는 준비 단계의 진행 막대에는 값을 적지 않는다(ARIA).
- 준비가 60초 넘게 멈추면 회전 표시도 멈추고 글로 알린다. 대화 머리의 상태 줄은 돌지 않는 점으로 바꿨다(오래 도는 움직임).
- 아일랜드 버튼 테두리와 줄자 막대 테두리의 대비를 3:1 위로 올렸다. 대화 폭 손잡이는 키보드로 잡으면 먹색 굵은 선으로 보인다.
- 상태 줄의 작은 글자 버튼(켜기와 설정)도 누를 자리를 24px로 지킨다. `+` 손잡이는 28px(모바일 32px)다.
- 방향키로 옮겨 다니지 않는 막대 세 개(가구, 아바타, 문)의 역할을 `toolbar`에서 `group`으로 바꿨다.
- 자리가 모자라 고를 수 없는 공간 종류는 흐리게만 두지 않고 크기 자리에 “자리가 모자라요”라고 적는다.
- 말풍선과 아일랜드의 안쪽 여백을 4px 눈금(8, 12, 16)에 맞췄다.
- 새 문구에서 고친 것: “끌어서 옮기고, 크기를 알려주면”(주어가 바뀜) → “끌어서 옮길 수 있고, 크기를 알려주면”.

### 실제 iOS Safari (iPhone 17 시뮬레이터, iOS 26.1)

- `safaridriver`로 실제 Safari를 조작했다(모델은 `?model=off`). WebGL 3D, 대화 시트, 위 도구 줄이 402pt 폭에 들어온다. 손가락 누름으로 입력창 초점 → 보내기 → 소파 초안, 집 전체 → 벽의 `+` → 침실 붙이기, 문 누르기 → 문 막대, 문 끌기(벽 가운데에서 1m), 아일랜드 펼치기가 동작했고 페이지 오류는 없었다.
- 자동 조작 중에는 Safari가 화면 키보드를 띄우지 않는다. 그래서 일반 Safari로 다시 열고 시뮬레이터 창에 실제 클릭을 보내 입력창을 눌렀다. 한글 화면 키보드가 올라온 상태에서 대화 머리, 대상 칩, 입력창이 키보드 위에 남는다. Safari의 떠 있는 주소 알약이 입력창 아래 테두리를 몇 픽셀 덮는다(글자는 가리지 않는다).

- 처음 준비 시간은 네트워크에 따라 크게 달랐다(같은 600MB가 28초와 159초).
- Qwen3 0.6B는 고치기 전 5문장을 놓쳤다. 위의 바로잡기 뒤에는 3문장이다(“벽은 좀 더 따뜻한 느낌이면 좋겠어”에서 색을 고르지 않음, “푹 기대 앉을 만한 거”를 소파로 잡음, “책 읽는 아담한 방”의 유형). 고치기 전 조건에서 같은 자리에 Qwen3.5 0.8B f32(4문장을 놓침, 문장당 2.5초)와 Llama 3.2 1B f32(낮은 소파의 높이를 포함해 5문장을 놓침, 1.7초)를 넣어 견줬다. 뚜렷이 낫지 않아 가장 작은 Qwen3 0.6B를 그대로 둔다.
- 1B가 놓친 두 문장은 v5.4와 같다(“푹 기대 앉을 만한 거” → 소파, “책 읽는 아담한 방”의 유형). E2B는 뒤의 하나만 놓쳤다.
- 모델이 켜진 상태에서 키, 자세, 집 전체 명령 다섯 개는 모델을 거치지 않고 약 0.16초에 처리됐다.
- **아일랜드:** 새 프로필에서 처음 받을 때 펼쳐진 채 0%로 나타나고 7초 뒤 접혔다. 다 받으면 준비 중 → 준비 완료로 바뀐 뒤 사라졌다. 보관본을 불러올 때는 접힌 채 준비 중 → 준비 완료만 보였다.
- **사진 판별(SigLIP):** 실제 소파 사진을 붙여 보냈다. 사진 판별 모델을 처음 받을 때(약 149MB) 아일랜드가 “사진 판별 모델 받는 중”으로 펼쳐졌다가 준비 완료 뒤 사라졌고, 답은 “소파 62%, 라운지체어 31%, 의자 6%”로 후보 세 개를 보여 줬다. 페이지 오류는 없었다. 사진 판별 코드는 바꾸지 않았다.

### 확인 범위와 한계

- v5.4에 적은 한계 가운데 닫은 것: 문을 옮기거나 지울 수 없음, 설비가 두 안만 견줌, 이름표가 아래로만 밀림, f16 없는 경로 미확인, 사진 판별 모델의 내려받기 알림을 실제로 돌리지 않음, 다시 시도 간격 없음, 알림을 멈출 수 없음, Safari와 Firefox 미확인, 옛 화면 세 장.
- 아바타는 키만 실제 값이고 비율과 앉는 높이는 단순 모형이다. 공간은 직사각형이고 맞닿은 공간 한 쌍마다 문은 하나다. 창문과 임의 벽은 없다. 방 편집 3D의 문 높이 205cm는 가정이다.
- f32 경로는 이 Mac의 GPU에서 f16 확인만 꺼서 돌렸다. 실제로 f16이 없는 GPU, Windows와 Android GPU, 메모리가 모자랄 때의 실제 오류 문구는 확인하지 못했다.
- iOS는 시뮬레이터에서 모델을 끈 상태로 확인했다. 실제 아이폰과 iOS의 WebGPU 모델은 확인하지 못했다. Android는 에뮬레이터를 띄웠지만 이 기기에서 다른 에뮬레이터가 이미 돌고 있어 방해하지 않으려고 바로 껐다. 확인하지 못했다.
- Firefox와 WebKit은 Playwright가 배포하는 빌드다. 정식 Firefox와 Safari 데스크톱 앱에서는 돌리지 않았다.
- 문이 두 벽에 난 좁은 화장실은 두 크기(1.8×2.2, 2.4×2.6m)에서만 문 앞이 비는 것을 검사했다. 더 좁거나 문이 세 개면 여유 5cm를 침범할 수 있다.

### 추가 요청: 모델 내려받기 안내와 더 가벼운 모델

- **조사:** Gemma 4 E2B, E4B의 브라우저용 빌드는 모두 지금 쓰는 Gemma 3 1B보다 무겁다. Hugging Face API로 파일 크기를 합산했다(2026-11-14).

| 빌드 | 내려받는 크기 | 비고 |
| --- | --- | --- |
| `mlc-ai/gemma3-1b-it-q4f16_1-MLC` (지금 기본) | 약 600MB | GPU 메모리 약 0.7GB |
| `mlc-ai/gemma-4-E2B-it-q4f16_1-MLC` | 약 2.8GB | GPU 메모리 약 3.4GB, shader-f16 필요. WebLLM 0.2.86부터 기본 목록에 있음 |

| `litert-community/gemma-4-E2B-it-litert-lm` (web) | 약 2.0GB | LiteRT-LM JS는 초기 미리보기이고 JSON 스키마 제약이 없다 |

  “E2B”는 유효 파라미터 2.3B라는 뜻이고 층별 임베딩 표까지 합치면 5.1B여서 내려받는 양이 크다. 그래서 기본은 가장 가벼운 Gemma 3 1B로 두고, Gemma 4 E2B는 `이 기기의 AI` 도구에서 직접 고를 때만 쓰게 했다. 두 모델 모두 같은 JSON 스키마 제약과 같은 검증 경로(`interpret.js`)를 쓴다. E4B는 넣지 않았다.
- **내려받는 중 다이얼로그:** 모델 파일을 처음 받을 때 이름, 크기, 진행률(줄자 모양 막대)을 보여 준다. `계속 쓰기`를 누르면 방 위의 작은 진행 표시로 줄고, `취소하고 모델 끄기`는 받기를 멈추고 그 선택을 기억한다. 사진 판별 모델도 20MB 넘는 파일을 실제로 받을 때 같은 다이얼로그를 쓴다.
- **실제 다운로드로 찾아 고친 문제 네 가지:**
  1. 로더는 설정과 토크나이저(약 34MB)를 받은 뒤에야 첫 진행 상황을 보낸다. 처음 20초 넘게 다이얼로그가 뜨지 않았다. Worker가 브라우저 캐시(`webllm/model`)에 가중치 조각이 없으면 먼저 시작을 알리게 했다.
  2. 라이브러리의 `hasModelInCache`는 받아 둔 모델도 없다고 답했고, 로더의 "Start to fetch params" 문장은 보관본을 불러올 때도 나온다. 둘에 기대면 다시 방문할 때마다 다이얼로그가 잠깐 떴다. 캐시를 직접 세고 전용 시작 신호를 쓰게 바꿨다. 보관본을 불러올 때(1B 약 1.6초, E2B 약 3.6초)는 다이얼로그가 뜨지 않는 것을 확인했다.
  3. 준비에 실패하면 Worker가 정리하면서 "내렸다"는 신호를 먼저 보내 상태가 꺼짐으로 바뀌고 실패 이유가 버려졌다. 다이얼로그가 0%에 멈춘 채 남았다(평가 실행이 60분 동안 멈춰서 발견). 준비 중에는 그 신호로 상태를 바꾸지 않게 고쳐 실패 이유와 `다시 시도`가 나온다.
  4. 받기 시작 직후 로더의 시작 문장을 "다 받았다"로 읽어 약 20초 동안 "받은 모델을 준비하는 중 100%"가 보였다. 90% 넘게 받은 뒤에만 준비 단계로 넘기게 고쳤다.
- 받은 양이나 준비 단계가 60초 넘게 그대로면 네트워크나 메모리를 확인하라는 안내를 덧붙인다. 실패 이유는 로더의 영문 오류 대신 네트워크, 저장 공간, GPU 메모리 중 무엇인지 우리말로 적는다.

- **`open-design` 규칙집 대조로 고친 것:**
  - 동작 줄이기 설정에서 애니메이션 길이만 0.01ms로 줄여 회전과 깜빡임이 매 프레임 되풀이될 수 있었다. 반복 횟수도 1로 고정했다(`animation-discipline`, WCAG 2.3.1).
  - 실패를 알리는 다이얼로그는 `alertdialog`로, 준비가 60초 넘게 멈추면 안내를 더하게 했다(`state-coverage`의 오류 구성과 준비 시간 기준).
  - 숫자 입력은 첫 글자부터 "범위로 입력해 주세요"를 띄웠다. 입력을 마쳤을 때만 이유와 지금 값을 알리고, 맞는 값이 되면 바로 지운다(`form-validation`, `state-coverage`).
  - `+` 메뉴의 묶음에 `group` 역할을 주고, 메뉴 항목이 아닌 것이 섞여 있던 공간 목록은 메뉴 역할을 뗐다(`accessibility-baseline`의 ARIA 규칙).
  - 모바일에서 이름표 높이를 30~32px로 키웠다(터치 영역 AA 기준 24px 이상).
- **`unslop` 대조로 고친 것:** 고른 공간 이름표의 `방 편집`을 줄자 노랑으로 칠했었다. 노랑은 직접 정한 치수와 선택 표시에만 쓰기로 했으므로 중립색으로 바꿨다. 준비 단계의 줄자 막대 깜빡임을 빼고 기존 회전 표시 하나만 남겼다. 새 스타일의 간격을 4px 눈금에 맞췄다.
- **최종 화면 품질 점검:** 데스크톱 1440×900과 모바일 390×844와 320×640의 새 화면 23장을 원본 크기로 보고 고쳤다. 집 전체 3D에서 뒤쪽 방의 이름표가 앞쪽 방 위에 놓여 어느 방의 이름인지 헷갈리던 것을 자기 방 바닥 위로 옮겼다. 방 편집 화면의 문 이름은 3D 글자 그림(한글 자간이 벌어지고 치수 라벨과 겹침)에서 화면 위 이름표로 바꾸고, 누르면 그 공간으로 가게 했다. 앉힌 의자를 고르면 키 이름표가 도구 막대 밑에서 머리를 가리던 것을 숨겼다. 모바일에서 공간 목록이 아래 버튼 줄에 가려지던 것, 시트를 끝까지 올렸을 때 위쪽 틈으로 모형 조각이 비치던 것, 모델 카드의 크기 표기가 어색하게 줄바꿈되던 것, 높이 비교 그림이 왼쪽에 치우치던 것을 고쳤다. 끌어 돌린 뒤 `화면 맞춤`을 눌러도 관성으로 카메라와 이름표가 계속 흘러가던 문제도 고쳤다(CI의 느린 렌더링에서 테스트가 시간 초과로 실패해 발견).
- **`humanize-korean` 빠른 규칙 대조:** 새로 쓴 UI 문구와 문서에서 번역투, 이중 피동, 관용 표현을 찾았고, 고칠 곳은 나오지 않았다.
- **a2ui 저장소에서 가져온 것:** `a2ui-project/a2ui`(v1.0, Apache-2.0)를 읽었다. 카탈로그를 렌더러와 에이전트의 계약으로 두고 구성요소 등록과 맞는지 검사한다는 방식을 가져와, `SURFACE_KINDS`와 `surfaces.jsx`의 구성요소, 아이콘, 안내 문장, `+` 메뉴가 서로 맞는지 보는 단위 검사를 추가했다(`src/catalog-parity.test.js`). 구성요소 트리와 데이터 바인딩을 모델이 직접 쓰게 하는 방식은 가져오지 않았다. 그 저장소도 작은 모델에서는 오류가 는다고 적고 있고, 이 앱은 스키마로 묶은 짧은 선택만 모델에 맡긴다. A2UI 프로토콜 호환은 여전히 주장하지 않는다.

`eval/chat/run.mjs`를 프로덕션 빌드에 대고 실행했다. 두 모델 모두 같은 예시 방에서 시작해 같은 18문장과 앱 명령 6문장을 보냈다. 결과는 `eval/chat/results/gemma3-1b-v54.json`, `gemma4-e2b-v54.json`.

- 1B가 놓친 것: “푹 기대 앉을 만한 거”를 라운지체어가 아닌 소파로 잡음, “책 읽는 아담한 방으로 꾸며줘”에서 공간 유형이 서재로 바뀌지 않음(v5.1 기록과 같다).
- E2B가 놓친 것: “책 읽는 아담한 방으로 꾸며줘”에 유형을 되묻기만 함, “벽은 좀 더 따뜻한 느낌이면 좋겠어”에서 색을 고르지 않음(앞선 실행에서는 웜그레이를 골랐다. 실행마다 달랐다). “푹 기대 앉을 만한 거”는 라운지체어로 맞혔고, 되돌리기, 공간 목록, 저장 같은 명령은 앱이 바로잡지 않아도 맞게 골랐다.

- 모델이 켜진 상태에서 앱 명령 다섯 개(“내 키 175cm로 침대에 눕혀줘”, “의자에 앉혀줘”, “일으켜줘”, “집 전체를 3D로 보여줘”, “아바타 숨겨줘”)는 모델을 거치지 않고 약 0.16초에 처리됐다. “의자에 앉혀줘”처럼 아바타라는 말이 없는 자세 명령은 아바타가 방에 보일 때만 앱이 읽는다.
- 실제 내려받기 화면: 새 프로필에서 다이얼로그가 바로 0%로 뜨고, 약 20초 뒤부터 받은 양이 올라가며, `계속 쓰기`로 접으면 작은 표시에 진행률이 이어지고, `취소하고 모델 끄기`를 누르면 꺼짐으로 기억되는 것을 확인했다.

### 확인 범위와 한계

- 아바타는 키만 실제 값이다. 팔다리 비율, 앉는 면 높이, 침대의 눕는 면은 이 앱이 그리는 가구 형상에 맞춘 단순 모형이고 실제 제품의 좌석 높이, 깊이와 다를 수 있다. 소파처럼 좌석이 깊게 그려지는 가구에서는 기대앉은 자세가 실제보다 뒤로 누워 보일 수 있다. 안내 문구는 “모형 기준”으로 적는다.
- 집 전체는 직사각형 공간을 잇는 방식이다. 문은 맞닿은 벽마다 80cm 하나를 가운데에 자동으로 그린 초안이고 위치를 옮기거나 지울 수 없다. 임의 벽과 창문 편집, 전체 3D에서 가구를 직접 옮기는 편집은 없다. 화장실 설비는 좌우를 뒤집은 두 가지 안 중에서만 고른다. 문이 두 벽에 나면 한쪽 문 앞을 설비가 일부 가릴 수 있다.
- 방 편집 3D에서 높은 벽의 문은 문 높이 205cm를 가정해 뚫는다. 실제 문 높이가 아니다.
- 화면 위 이름표는 겹치면 아래로만 민다. 공간이 많고 화면이 좁으면 이름표가 자기 공간에서 멀어질 수 있다.
- 실제 모델은 Mac Chrome 한 기기에서만 확인했다. f16을 지원하지 않는 GPU의 경로(Qwen3 0.6B, Gemma 4 E2B q4f32), Windows와 Android GPU, 메모리가 작은 기기에서 E2B가 실패할 때의 실제 오류 문구는 확인하지 않았다. 오류 설명은 흔한 영문 오류 문구에 맞춘 것이다.
- 사진 판별 모델(SigLIP)의 내려받기 다이얼로그는 진행 상태를 넣어 본 화면 검사와 코드 경로로만 확인했고, 실제 사진으로 다시 돌리지 않았다. 사진 판별 코드는 바꾸지 않았다.
- 내려받기 실패 뒤 다시 시도에는 횟수 제한이나 간격 조절이 없다. 잠깐 뜨는 알림은 4초 뒤 사라지고 멈출 수 없다.
- Safari, Firefox와 실제 휴대폰의 가상 키보드와 터치는 확인하지 않았다. 모바일은 Chrome의 390×844와 320×640 화면과 터치 에뮬레이션으로 확인했다.
- 전역에 설치한 `maker-pipeline`과 스킬들은 이 저장소 밖(`~/.agents/skills`, `~/.claude`, `~/.codex`)에 있다. 팀원 기기에는 저장소 안의 `.agents/skills/`만 따라간다.

## v5.3 화장실 포함 집 전체 3D와 다음 세션 프롬프트

- 요청: 집 전체도 화장실을 포함해 3D로 보고, 다음 세션에서 디자인, 기능과 앞선 팀원 의견의 반영 상태를 리뷰하고 수정할 수 있는 프롬프트를 제공한다.
- 방별 3D 렌더러를 전체 보기에서도 재사용한다. 전체 2D와 같은 공간 오프셋에 모든 방과 가구를 놓고, 공유 벽, 80cm 문 구간, 변기, 세면대, 샤워 공간을 만든다. 아바타가 속한 방을 활성 방과 따로 찾아 전체 3D에도 표시한다.
- 전체 보기에서도 기존 2D/3D 버튼을 사용한다. 2D에서 공간 배치, 3D에서 회전, 확대, 공간 선택, 두 번 눌러 방 편집, 현재 3D 화면의 PNG 저장을 지원한다. “집 전체를 3D로 보여줘”는 보기까지 지정한다. 저장 형식은 v4를 유지한다.
- `npm run verify`: 공용 스킬 연결, 소스 43개 문법, 단위 테스트 62개, 프로덕션 빌드 통과. `npm run format:check`, `git diff --check` 통과.
- `npm run test:e2e`: Chrome 20개 통과. 기존 17개 흐름을 보존하고 집 전체 3D 검사 3개를 추가했다.

## v5.1 모델 우선 해석과 실제 사진 평가

요청: 실제 사진으로 사진 모델 정확도를 재고, 규칙은 대체 경로로 두고 기본은 모델이 해석하게 한다.

### 실제 사진 정확도 (`eval/photo/`)

- **사진:** Openverse(Flickr, StockSnap, rawpixel 등)와 Wikimedia Commons에서 CC 라이선스 사진 후보 약 750장을 받아, 가구가 주인공인 사진을 사람이 직접 보고 20종마다 5~6장, 모두 118장을 골랐다(제품 사진 79장, 다른 가구가 함께 있는 방 사진 39장). 정답은 고른 사람이 정했다. 종류마다 반씩 무작위로 나눠 dev 60장은 모델, 질문, 기준값을 고르는 데만 쓰고, test 58장은 마지막에 한 번만 쟀다. 사진 파일은 저장소에 넣지 않고 주소, 작성자, 라이선스를 `manifest.json`에 남겼다.
- **실행:** 앱의 사진 경로(`imageData` → Worker)를 Mac Chrome(WebGPU, shader-f16)에서 그대로 실행했다. 채점은 앱과 같은 함수를 쓴다.
- **기준선(배포 중이던 2792c0c):** SmolVLM 256M 설명 + 규칙 단어 찾기. test 58장 중 맞는 종류로 초안 29.3%, 틀린 종류로 초안 17.2%, 종류 못 찾음 19.0%, 설명을 버림 34.5%(“Bed.”처럼 한 단어 답도 버리던 필터 문제 포함). 전체 118장은 25.4%.
- **dev에서 비교한 것:** SmolVLM에 보기 목록에서 고르게 하면 15%로 더 나빠졌다(앞쪽 보기 sofa, bed만 반복). 설명 질문을 바꿔도 33~37%. CLIP ViT-B/32 68.3%, SigLIP base 80~85%. SigLIP 4비트(q4f16) 81.7%와 상위 3개 98.3%로 크기 대비 가장 나아 채택했다. 초안을 바로 만들 기준 확률 0.7도 dev에서 정했다.

| 실행 방식 | 1순위 정답 | 상위 3개 안 | 초안 맞음 | 초안 틀림 | 후보에서 고름 | 후보에 없음 | 사진 1장 |

- 틀린 경우는 대부분 비슷한 가구끼리다. 장식장과 옷장을 수납장으로, TV장을 수납장으로, 소파테이블이 앞에 있는 거실 사진을 소파테이블로 봤다. 사진만으로 cm를 재지 않으며 크기는 유형 기본값이다.

### 모델 우선 해석

- 사이트를 열면 WebGPU가 있으면 Gemma 3 1B를 자동으로 준비한다. 준비되면 모든 문장을 모델이 먼저 해석하고(JSON 스키마 제약), `src/app/interpret.js`가 숫자, 이름, 말하지 않은 속성과 문장에 없는 동작을 검증한다. 준비 중, 꺼짐, 미지원, 25초 초과, 형식 오류면 규칙이 처리하고 이유를 턴에 적는다.
- **실제 Gemma, 같은 대화 18문장(`eval/chat/`)**, 턴당 1.8~2.7초:
  - 1차(검증 보강 전): 모델 혼자 맞힌 것은 크기 느낌, 깊이, 색, 놓기, 회전, 책상 치수 등 9개 정도. “빈 방으로 시작할래”를 소파 초안으로, “되돌려줘”와 “공간 목록 보여줘”와 “겹친 가구 정리해줘”를 놓침. “배치를 파일로 저장하고 싶어”에서 “배치”를 놓기로 읽어 책상을 방에 놓음. 내 코드의 벽 색 검증 버그와 “하나 놓고 싶어”를 새 가구로 보지 못한 문제도 찾음.
  - 수정: 문장에 명령(되돌려, 저장, 공간 목록, 빈 방 등)이 분명하면 모델 선택 대신 명령을 따르고 바로잡은 내용에 남김. 놓기 동작은 “놓아/놔 줘/배치해” 같은 동사가 있을 때만. 벽 색 검증 버그 수정. 방 이야기(“~방으로 꾸며줘”) 판별을 검증에 추가.
  - 최종: 18문장 중 16개가 기대한 결과. 모델이 혼자 맞힌 문장 6개(따뜻한 벽 → 샌드, 2인 낮은 소파 170과 높이 65, 깊은 좌석 100, 네이비, 놓기, 90도 회전), 앱이 바로잡아 맞게 처리한 문장 10개(명령 6개, 문장의 이름과 숫자에 맞춘 4개). 다르게 처리된 2개: “책 읽는 아담한 방으로 꾸며줘”에서 공간 유형이 서재로 바뀌지 않고 천장만 바뀜, “푹 기대 앉을 만한 거”를 라운지체어가 아닌 소파로 잡음.
  - 결론: 1B 모델은 크기 느낌, 색, 이어지는 수정은 잘 읽지만 명령형 문장의 의도는 자주 놓친다. 그래서 명령어가 분명한 문장은 앱이 바로잡는다. 더 큰 모델을 쓰면 나아질 수 있지만 내려받는 크기가 커서 이번에는 바꾸지 않았다.
- 화면: 답 아래에 “Gemma가 해석, 앱이 숫자와 범위 확인”, 바로잡았으면 “앱이 2곳 바로잡음”(눌러서 내용 확인), 규칙이면 “상담 모델 준비 중이라 규칙으로 처리”. 입력창 아래 상태줄에 모델 준비 진행률, 끄기, 켜기. 해석 중에는 그 턴에 “문장을 해석하는 중”과 멈추기.

## 남은 환경별 확인 범위

모든 모바일 기기, Safari, Firefox, GPU를 검증한 것은 아닙니다. GPU/메모리 부족 시 AI 모델 준비가 실패할 수 있고, 사진 CPU 모드는 기기에 따라 느립니다. 직접 입력, 규칙 기반 상담, 2D 배치는 별도 모델 없이 작동합니다.

GPU, WebGL, 로컬 저장소를 차단한 별도 브라우저 컨텍스트에서도 2D로 열리고 자동 저장 불가 상태를 안내하는 것을 확인했습니다.

실제 네트워크 기록에서 ONNX WASM은 버전이 고정된 jsDelivr 주소로 로드됨을 확인해, 빌드에 중복 포함되던 미사용 26MB WASM 파일을 배포물에서 제외했습니다. 제외 후 사진 추론도 재확인했습니다.
